## 결정
2026-10-09 할 일 기록 도구(시작·완료·하위 항목·작업 중 결정) 설계 중 사람이 말한 것을 그대로 적는다.

사람: "모든건 다 KST 기준으로 하셈"
AI가 범위를 물었고(할 일 기록만 / 사람이 보는 모든 시각 / 계약 데이터까지), 사람이 "사람이 보는 모든 시각"을 골랐다.

(AI 해석)
1. 사람이 읽는 형태로 쓰거나 보여 주는 시각은 전부 KST(+09:00)다: 할 일 기록(`tasks/`), 결정 문서의 `date`, `demo/BUILT_HERE.md`의 시각 칸, `logs/*.log`와 stderr 로그의 시각, cop-ui 화면의 시각 표시.
2. 코드는 기계 시간대 설정을 믿지 않고 `Asia/Seoul`(또는 고정 +09:00)을 직접 지정한다. 팀원 노트북(WSL)이 UTC여도 같은 결과가 나와야 한다.
3. 저장할 때 사람이 읽는 시각 문자열은 오프셋을 붙인 ISO 8601로 쓴다(예: `2026-10-10T12:03:15+09:00`).
4. 계약(contracts)의 `t_ms`는 epoch 밀리초 숫자 그대로 둔다. epoch 밀리초는 1970-01-01 00:00 UTC부터 센 값이라 시간대와 무관하므로 바꿀 것이 없다. 화면에 보일 때만 KST로 바꾼다.
5. 정책 3의 문구는 사람만 고칠 수 있다(POLICY.md). 제안 문구: "좌표는 WGS84 위경도(도), 고도는 m, 시간 값은 epoch 밀리초(`t_ms`). 사람이 보는 시각은 전부 KST(+09:00)로 쓰고 보여 주며, 코드는 기계 시간대가 아니라 Asia/Seoul을 직접 쓴다."

## 이유
- 대회·통합 시각(10/10 18:00 등)이 전부 KST로 정해져 있어 기록과 화면이 같은 기준이어야 진행 상황을 바로 읽는다.
- 확인한 문제: `scripts/decide.py`는 `date.today()`(기계 날짜), `shared/log.py`는 기계 시각을 쓴다. 기계가 UTC면 KST 00:00~09:00에 만든 결정에 전날 날짜가 찍힌다.

## 버린 대안
- 할 일 기록만 KST: 결정 날짜·로그·화면이 기계마다 달라지는 문제가 남는다.
- 계약 데이터의 시간 필드까지 KST 문자열로: 계약·예시 JSON·TS·스파이크를 다 고쳐야 하고 10/10 12:00 형식 고정 전에 끝내기 어렵다. epoch 숫자는 시간대와 무관하므로 얻는 것도 없다.

## 영향
- `scripts/decide.py`의 날짜를 KST로(`datetime.now(ZoneInfo("Asia/Seoul")).date()`).
- `shared/log.py` Formatter의 시각을 KST로(converter 지정, 오프셋 표시).
- 새 할 일 기록 도구(`scripts/task.py`, `tasks/log.jsonl`, `tasks/NOW.md`)는 처음부터 KST 문자열로 저장·표시.
- cop-ui에서 시각을 표시하는 곳은 `Asia/Seoul`로 포맷(리드 담당, 화면 작업 때).
- `demo/BUILT_HERE.md` 시각 칸은 KST로 적는다.
- POLICY.md 정책 3 문구 수정은 리드가 직접.
