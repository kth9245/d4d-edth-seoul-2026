# 표적 위협도 + RF 방출 감지

상태: **구현됨(Part2-28, main 반영).** 화면은 리드(Part1-27). 결정 0039(규칙)와 0040(보정)이 정본이고, 이 문서는 그 설명이다. 다르면 결정이 맞다.
작성: 최동호 (2026-10-10), 담당 최동호. 접근 1(sensing에 둔다)로 합의.
개정 이력
- 초안: "알림만" 구조를 "위협 누적 뒤 대응 승인 요청"으로, 속력·접근 측정을 점수×시간 누적으로 바꿈.
- 개정 2: 스파이크(틱 루프 실행) 결과로 기준치를 0.70 → 0.40으로 낮춤(보트를 발견하면 결국 대응 판단을 해야 하므로 boat1도 대상). 결정 0039.
- 개정 5: 결정 0043. 근접 단계를 반경 **3배**로 넓히고(0041의 2배는 boat3 수치를 잘못 계산한 것), **발견 카드는 누적이 기준에 찰 때만** 올린다.
- 개정 4: 결정 0041. 기준점 반경 밖이라도 **반경 2배 안이면 +0.15**(근접 단계). 반경 안에 못 들어가는데 계속 다가오는 보트(boat2·boat3)가 기준치 0.40에서 빠지는 문제를 푼다.
- 개정 3: 리드 답을 반영한 결정 0040. **별도 위협 카드를 없애고** 기존 발견 카드(`target_detected`)에 점수·이유를 보인다. 종류는 스캔으로 판별. 화면은 리드. 시나리오 B 숫자로 갱신.

## 1. 목적

표적의 위협도를 매 틱 계산하고, 운영자가 보는 발견 카드에 **관측 위험 점수와 이유**를 보여 준다. 미결 카드는 점수순으로 정렬해 더 급한 표적이 위에 오게 한다.

원칙
- 규칙은 시나리오에 맞춰 조정하지 않는다. 일반 규칙을 정하고 시연 결과는 그대로 받아들인다. 시연에서 보여 줄 장면을 위해서는 규칙이 아니라 시나리오 값(방출 시각, RF 범위)을 맞춘다.
- RF는 "출력이 클수록 중요하다"로 보지 않는다. **표적이 방출을 하는가**를 단서로 쓴다.
- 점수는 확률이 아니라 시나리오용 휴리스틱이다. 화면에는 "관측 위험 점수"로 표시하고, RF 방출이나 속도를 적대성의 확정 증거로 설명하지 않는다.
- 화면에는 우리가 잡은 것(`rf_detected`)만 보인다. 정답인 `emitting`은 화면에 쓰지 않는다.
- 점수는 운영자 검토용 참고이며 어떤 기체에도 명령을 내지 않는다. 자동 표적 지정·교전 판단이 아니다.
- 가상 데이터만 쓴다.

## 2. 접근과 담당

| 부분 | 내용 | 담당 |
|---|---|---|
| sensing `score_target`(SNS-03) | 점수·이유·누적을 계산하는 순수 함수 | 최동호 |
| sim `update_emission`(SIM-14) | 적이 방출 시각이 되면 `Target.emitting` 켜기 | 최동호 |
| gateway `score_targets`(GW-10) | 틱마다 점수를 `Target`에 쓰기. 종류는 `seen_by`가 비면 unknown | 최동호 |
| `engine.py` | 호출 순서만: 1.6 `update_emission`, 2.5 `score_targets` | 최동호 |
| cop-ui | 카드에 점수·이유, 점수순 정렬, 지도 "RF" 이름표, "스캔 판별: …" 문구 | 리드(Part1-27) |

카드는 새로 만들지 않는다. `ReportKind.threat_high`, `Report.threat`·`speed_mps`는 없다. 화면이 카드의 `target_id`로 `Target`을 찾아 `threat`·`threat_reasons`·`rf_detected`를 읽는다(runtime의 카드 생성은 건드리지 않는다).

기각한 안
- assess 모듈 부활: 리드 영역이고 결정 0007을 뒤집어야 한다.
- UI만 계산: 서버가 점수를 줘야 정렬·표시가 일관된다.
- 별도 위협 카드(`threat_high`, 개정 2까지의 안): 같은 표적에 카드가 두 장이 된다(결정 0040).
- 위치 변화로 속도 측정(기준 샘플 + 10 s 윈도우): 필드가 늘고 관찰 끊김 규칙이 필요하며 잡음 없는 시뮬레이션에서는 순간 속도와 결과가 같다. 순간 속도로 대체.
- 접근 속도, 체류 시간, 방출 수준: 데모에서 쓰임이 없다.
- 점수 구간별 확인 시간 표: 경계에서 결과가 뚝 바뀐다. 점수×시간 누적으로 대체.

## 3. 데이터

### 입력 (시나리오)

| 위치 | 필드 | 의미 |
|---|---|---|
| `EnemySpec` | `emit_start_offset_ms: int \| None` | **등장 후** 이 시각부터 계속 방출한다. `None`이면 무음 |
| `VehicleSpec` | `rf_range_m: float = 0` | RF 수신 범위(m). 0이면 수신 불가 |
| `Scenario` | `watch_points: list[WatchPoint]` | 지킬 지점 목록 |
| `WatchPoint` | `id`, `name`, `pos`, `radius_m` | 점수의 "반경 안" 판정 |

데모 값(`demo/scenarios/baengnyeong_night.json`)
- d1·d2·d3: `rf_range_m = 2000`. usv·ugv: 0.
- `watch_points`: 상륙 예상 지점 1개(37.978, 124.70), 반경 2000 m. 기존 landing 플레이의 좌표를 그대로 쓴다.
- boat2: `emit_start_offset_ms = 360000`(등장 11:00 + 6분 = 17:00). 나머지 적은 무음. 시나리오 B에서 boat2의 발견 카드는 16:22에 뜨므로 **방출은 카드가 뜬 뒤**에 시작된다(결정 0040 리드 7번).

### 출력 (`Target`, 실행 중)

| 필드 | 계산 주체 | 의미 |
|---|---|---|
| `emitting: bool` | sim | 방출 시각이 지나면 true. 정답이라 화면에 쓰지 않는다 |
| `rf_detected: bool` | sensing | 방출 중이고 RF 범위 안에 살아 있는 기체(`ready`·`active`)가 있으면 true. 시각 스캔(`seen_by`)과는 별개다 |
| `threat: int` | sensing | 점수. 0.01 단위 정수(0.57 → 57), 0~100 |
| `threat_reasons: list[str]` | sensing | 실제로 더해진 요소의 이유 코드 |
| `threat_accum: int` | sensing | 점수가 기준치 이상이고 관찰 중인 동안 쌓은 점수(0.01 단위)×ms. 아니면 0. 현재는 **기록만** 한다(7절) |

그 밖의 입력은 기존 데이터다: 종류, 위치, `seen_by`, sim의 순간 속도(`vel_east_mps`, `vel_north_mps`; 속력 = √(동² + 북²)), 거리는 `shared.geo.dist_m`.

## 4. 점수 (순수 함수, 상한 1.00)

점수는 정수(0.01 = 1)로 계산한다.

| 요소 | 조건 | 가산 | 이유 코드 |
|---|---|---|---|
| 종류 기본점 | fast_boat / boat / person·unknown | 0.40 / 0.20 / 0.30 | `kind_fast_boat` 등 |
| 기준점 반경 안 | 어떤 `watch_point` 반경 안 | +0.30 | `inside_watch_radius` |
| 기준점 근접 | 반경 밖이지만 반경의 3배 안 (결정 0041, 0043) | +0.15 | `near_watch_radius` |
| RF 방출 | `rf_detected` | +0.30 | `rf_emission` |
| 속도 | 속력 1 m/s당 +0.05, 상한 +0.30. **관찰 중일 때만** | 0 ~ +0.30 | `speed` |

- 합계 상한 1.00은 마지막에 적용한다.
- **종류는 스캔으로 판별한다(결정 0040).** 아군 기체 센서에 한 번도 잡히지 않았으면(`seen_by`가 비고 `first_seen_ms`가 0) 종류를 미상(0.30, `kind_unknown`)으로 계산하고, **한 번 잡힌 뒤부터는 지금 안 보여도 실제 종류를 유지한다.** (지금 보고 있는지로만 판단하면 스캔을 놓치는 순간 종류가 미상으로 되돌아가 점수가 오히려 올라간다.) 속도 가산과 누적은 지금 스캔 중일 때만 적용한다. 화면은 `kind_<종류>`가 이유에 있으면 "스캔 판별: 고속정"처럼 표시한다.
- RF는 시각 스캔과 별개라서, 스캔 전이라도 방출 중이고 수신 기체가 범위 안이면 `rf_detected`가 켜진다. 예: 스캔이 끊긴 boat2는 종류 보트 0.20 + 근접 0.15 + RF 0.30 = 0.65(속도 가산만 빠진다).
- `threat_reasons`는 점수 계산과 같은 규칙에서 나온다.
- 가산치, 속도 계수(0.05/(m/s))와 상한(0.30)은 **임의 값**이다. 시연에서 돌려 보고 조정한다.
- 멈추면 속도 가산이 사라진다.

가능한 점수 조합 (속도 가산 제외, **스캔된** 표적)

| 종류 | 기본 | + 근접(3배 안) | + 반경 안 | + RF | + 반경 안 + RF |
|---|---|---|---|---|---|
| fast_boat | 0.40 | 0.55 | 0.70 | 0.70 | 1.00 |
| boat | 0.20 | 0.35 | 0.50 | 0.50 | 0.80 |
| person·unknown | 0.30 | 0.45 | 0.60 | 0.60 | 0.90 |

근접 단계가 없으면 반경에 못 들어가는 boat는 속도(최대 0.30)나 RF가 더해져야 기준치 0.40에 닿는다. 시연에서 boat2·boat3는 반경 안에 한 번도 못 들어간다. 기준점까지 거리는 반경 배수로 boat2 약 1.5배, boat3 2.4배(11:00)에서 2.0배(25:00)까지다. 2배 근접 단계(0041)는 boat3를 놓쳤고, 3배로 넓혀(0043) 두 척 모두 0.42가 된다.

### 4.1 위협 누적 (점수 × 시간)과 카드 거르기

점수가 **기준치 0.40 이상이고 관찰 중인 동안** `점수 × 틱 길이(ms)`를 `threat_accum`에 더한다. 그렇지 않으면 0으로 리셋한다(서서히 줄이지 않는다). 점수 1.0으로 4.5초 쌓이면 `450 × 1000 = 450000`이다(`CARD_ACCUM`, sensing이 공개). 점수가 높을수록 빨리 넘는 연속 규칙이라 구간 경계가 없다.

| 점수 | 기준값 4.5까지 |
|---|---|
| 1.0 | 4.5 s |
| 0.8 | 약 5.6 s |
| 0.5 | 9.0 s |
| 0.42 | 약 10.7 s |
| 0.4 | 약 11.3 s |
| 0.4 미만 | 누적하지 않음 |

**발견 카드는 누적이 `CARD_ACCUM`에 찰 때만 올라간다(결정 0043).** runtime의 순찰 step `target_found` 조건이 "표적을 관찰 중이고 아직 카드가 없다"에 더해 `threat_accum >= CARD_ACCUM`을 요구한다. 기준 미만이면 점수는 `Target`에 기록만 되고 카드는 뜨지 않는다. 추적 중인 자기 표적(타격 승인 카드 쪽)은 영향이 없다. 관찰이 끊기거나 점수가 0.40 아래로 내려가면 누적이 0이 되어 처음부터 다시 쌓는다.

기준치 0.4와 기준값 4.5는 **임의 값**이다.

## 5. 흐름

틱 순서(contracts/API.md §3): `spawn_enemies`·`steer_enemies` → **1.6 `update_emission`** → `observe` → **2.5 `score_targets`** → 입력 적용 → …

sim이 표적을 움직이고 `emitting`을 갱신 → sensing `observe`가 `seen_by`를 갱신 → `score_targets`가 `threat`·`threat_reasons`·`rf_detected`·`threat_accum`을 채움 → 화면(리드)이 카드의 표적을 찾아 점수·이유를 표시하고 미결 카드를 점수순으로 정렬한다. 무력화된 표적은 갱신하지 않는다.

### 5.1 카드 정렬

화면(리드)이 정한다. 문서 초안의 키는 `(점수 내림차순, 속력 내림차순, first_seen_ms 오름차순, id)`이고 표적과 무관한 카드(배터리 부족 등)는 아래에 둔다. `Report`에 점수를 복사해 두지 않고 `Target`의 현재 값을 읽으므로, 방출이 시작되어 점수가 오르면 카드가 실시간으로 위로 올라간다.

## 6. 시연 결과 (시나리오 B, 실제 틱 루프)

카드는 스캔된 뒤 누적이 찰 때 뜬다.

| 표적 | 카드 | 점수 변화 | 비고 |
|---|---|---|---|
| boat1 | 16:30 (d1) | 스캔 16:21에 **0.50**(반경 안) | 0.50이라 9 s 누적. 필터 전에는 16:21 |
| boat2 | 16:33 (d2) | 스캔 16:22에 **0.42**(근접 + 속도) → 17:00 방출 시작으로 **0.72** | 카드는 약 10.7 s 누적 뒤. 방출은 카드가 뜬 뒤이고, d2와 약 400 m에서 RF 감지 +0.30으로 boat1(0.50)을 넘어 카드가 맨 위로 올라간다 |
| boat3 | 18:33 (d2) | **0.42**(3배 근접) | 무음. 필터 전에는 18:17 |
| fast1 | 추적 중 승인 카드(usv 25:47 등) | 스캔 즉시 **1.00** | 종류 0.40 + 반경 0.30 + 속도 0.30. 방출 없음. 추적 카드라 필터 영향 없음 |

- 이 장면은 `modules/gateway/tests/test_demo_threat.py`가 고정한다(boat2 카드 16:32.8, 방출 17:00.0, 점수 0.42 → 0.72, boat1보다 높음).
- 3분 시연과 23분 시각의 관계: 모든 시각은 시뮬레이션 시각(`t_ms`) 기준이고 재생 속도와 무관하다.

## 7. 아직 안 된 것 · 열린 질문

1. ~~누적 기준으로 카드를 거르는 동작~~ 구현됨(결정 0043). 카드 시각이 5~11 s 늦어져서 리드의 화면 정지 시각과 QA 기대값을 맞춰야 한다.
2. **점수가 운영자 선택지에 영향을 주지 않는다.** 점수는 카드를 올리는 시점과 표시·정렬에만 쓰인다. 카드의 선택지("대응 승인", "계속 관찰")는 별도 위협 카드가 없어지며 대부분 의미가 사라졌으나 결정으로 닫지는 않았다.
3. 가산치, 기준치 0.4, 기준값 4.5는 임의 값이다. 시연에서 돌려 보고 조정한다.
4. RF 장면은 boat2 한 척뿐이다. fast1은 방출하지 않는다.
5. 스캔 전에도 RF는 켜진다(4절). 화면에서 의아해 보일 수 있다.
6. 지도에서 표적 옆에 점수를 보일지는 리드의 화면 결정이다.
7. `contracts/API.md` 데이터 설명 절에 새 `Target` 필드가 반영됐는지는 확인하지 않았다(틱 순서 표만 갱신).
