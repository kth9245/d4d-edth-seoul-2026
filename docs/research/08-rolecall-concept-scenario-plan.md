## 2. 아이디어: ROLECALL

### 2.1 한 문장
운용자는 기체를 한 대씩 조종하지 않는다. 결정 한 번으로 공중·해상·지상 기체가 함께 움직이고, 기체가 하는 모든 행동은 작전 전에 검토된 플레이 안에 있으며, 어떤 명령도 안전 하한선을 넘지 못한다.

주인공 장면(결정 0003): 드론이 미식별 선박을 보고하면 운용자가 "근접 확인"을 한 번 누르고, 그 순간 무인수상정이 접근하고 지상로봇이 상륙 예상 지점으로 가고 예비 드론이 빈 구역을 채운다. 편집기는 이 장면 앞에 짧게 보여 준다(기능이 장면보다 중요).

### 2.2 사용자 원문 아이디어
> 드론이 행동하는 시나리오를 워크플로우처럼 미리 정해 놓은 행동을 하게 한 다음, 그걸 특정 드론한테 역할로 부여하고 유동적으로. 이 행동을 UI로 조립할 수 있게 만들어서 프로그래밍 없이.

시연 주인공: 역할 입력 → 기체들이 역할대로 움직임 + 기체끼리 협동 + 운용자 실시간 개입 + 비상상황·실시간 계획 변경. 현장 반응은 반드시 보고 단계를 거친다. 공중·지상·해상 결합을 핵심으로 강조한다.

### 2.3 핵심 개념
- **플레이(play)**: step 카드들을 연결한 행동 설계. 카드 안에는 액션 줄(이동·감시·보고·신호·조건·반복)이 들어간다. 코드 없이 편집기에서 만든다.
- **역할(role)**: 플레이는 기체가 아니라 역할 단위로 쓴다(공중 관측, 해상 확인, 해안 감시). 실행 때 능력·거리·배터리로 기체를 붙인다. 운용자는 한 번 승인한다.
- **기체 종류별 펼침**: 같은 액션이 드론·무인수상정·지상로봇에서 다른 명령이 된다(펼치기 표). 할 수 없는 액션이 있는 기체는 그 역할 후보에서 빠진다.
- **보고 → 운용자 결정**: 기체는 발견한 것을 스스로 처리하지 않고 보고 카드를 올린다. 운용자가 선택지 중 하나를 누르면 그 선택에 연결된 step이 여러 기체에서 함께 시작된다.
- **비상 행동(전역)**: 통신 두절·배터리 부족·위치 이상·운용자 호출 때 할 행동을 플레이와 따로 정해 둔다. 어느 step에 있든 들어가고, 끝나면 원래 step으로 돌아온다.
- **하던 일 이어받기**: 기체가 빠지면 그 step을 할 수 있는 다른 기체가 같은 step부터 이어간다. 영역을 넘는 이어받기(드론 → 무인수상정)는 시연의 한 장면으로만 두고 핵심으로 내세우지 않는다(사용자 동의).
- **플랜 주입**: 실행 중에 라이브러리의 다른 플레이를 표적이나 구역에 놓는다. 바뀌는 배정을 먼저 보여 주고 승인 뒤 적용. 원래 일은 보류 목록에. 승인 전의 주입 플랜은 출처가 없으므로 기체 명령을 만들 수 없다(하한선 규칙 1).
- **AI 초안(결정 0003)**: 편집기에 문장을 넣으면 LLM이 정해진 어휘(액션·조건 목록)와 스키마로만 플레이 초안을 만든다. 초안은 사람이 고치고 저장 전 확인을 지나야 플레이가 된다. 시연 문장의 응답은 로컬 캐시에 두어 인터넷이 끊기거나 답이 달라져도 같은 결과가 나온다(결정 0001의 캐시 요구). DIU Orchestrator 챌린지의 "지휘관 의도(문장)를 플레이북으로"에 대응한다.
- **역할 공백(결정 0003)**: 기체가 빠졌는데 이어받을 기체가 없으면 그 역할은 "공백" 상태가 되고 상황판에 사건 카드로 올라온다. 공백이 이어진 시간을 잰다(인지부하 지표 3).
- **직접 조종**: 기체 하나를 골라 지도에서 지점을 찍어 움직인다. 놓으면 하던 step으로 복귀.
- **안전 하한선(팀 정체성, 결정 0003)**: 시나리오 step, AI 초안, 주입한 플랜, 직접 조종까지 기체로 나가는 모든 명령이 같은 문(safety)을 지난다. 규칙은 3개이고 지휘관 경고·예외 허가는 두지 않는다.
  1. **출처 없는 명령 거부**: 모든 명령은 어느 플레이·어느 step·어느 운용자 결정에서 나왔는지 출처를 달고 다닌다. 승인 안 된 AI 초안이나 승인 안 된 주입 플랜은 출처가 없어 실행 명령이 되지 못하고 "승인 대기"로만 올라간다.
  2. **작전 구역 밖 차단**: 작전 구역 밖으로 나가는 명령은 출처가 누구든 무조건 막는다. 작전 구역은 작전 설정에서 그리고 상황판에서는 바꿀 수 없다. 서해 시나리오에서 북쪽 경계는 NLL이다.
  3. **귀환 배터리**: 돌아올 배터리가 모자라면 명령을 막고 갈 수 있는 지점까지의 대안을 보여 준다.
  코드 구조로 보장: sim은 safety만 만들 수 있는 "통과한 명령" 형식만 받는다. 이름은 미 육군 2026-08 공모가 쓴 "policy-based control"에 맞춘다.
- **확인(검사) 범위**: 저장 전 확인은 로직 오류(끊긴 연결, 닿을 수 없는 step, 끝나지 않는 반복, 송신 없는 수신), 보고·승인 지점 누락, 귀환 배터리, 작전 구역 밖 경로. AI 초안과 수동 편집에 똑같이 걸린다. 서명·비상 처리 강제는 뺐다(사용자 지시: "지금은 아이디어만"). 금지구역은 별도로 두지 않고 작전 구역 밖 차단으로 대신한다.

### 2.4 차별화
- **SUPPORTY(지난 대회 수상)**: 음성 AI로 의도를 자산 제어로 바꾸고 Mission Queue로 자동 배정, 요청 4건 이상이면 인지부하 경보, 4G/5G↔Starlink 전환. 저장소 분석: 배정이 `Math.random()`, `pend>=4` 경보, Starlink 코드 없음, 실제 기체 2 + 직선 가짜 3. 보급·구출 임무 중심.
- **브레이브버드(지난 대회 미수상)**: 능력 벡터 기반 재배치 추천. 교훈: 배정만으로는 주인공이 못 된다.
- **ROLECALL의 주장(결정 0003)**: 결정 한 번에 세 영역 기체가 함께 움직이고, 기체가 하는 모든 행동은 작전 전에 검토된 플레이 안에 있으며, AI 초안·사람 편집·실행 중 주입·직접 조종이 전부 같은 문을 지난다. 편집기 자체는 새롭지 않다(MiR, FlytBase, PROMISE에 있음). 편집기는 "작전 전 계획 담당이 검토된 플레이북을 만드는 곳"으로 소개한다(DIU DAWG 국장의 "메뉴 클릭이나 행동 프로그래밍이 아니라"는 발언에 대한 대응). "조합의 새로움"이라는 문장은 쓰지 않는다.
- **SUPPORTY 언급**: 발표에서 언급하지 않는다(사람 결정). 질의에서 나오면 한 문장만: "저쪽은 여러 대를 말로 부를 수 있음을 보였고, 우리는 여러 대를 맡겨도 모든 행동이 검토된 범위를 못 벗어남을 보인다." 상대 코드를 근거로 삼지 않는다.
- 구조상 가장 가까운 선례: DARPA OFFSET CCAST 임무 계획기. 그 보고서의 지휘관 발언: "임무 계획 구조를 수정하거나 보완할 실질적 수단이 없다" — 우리 플랜 주입이 겨냥하는 지점.

## 3. 제품 흐름(완성 UI 상상)

사용자 확정 순서: **작전 만들기 → 육·해·공 기체 선택 → 기체별 시나리오 작성 → 시뮬레이션 → 실행·상황판**. 전체 작전을 시나리오로 저장한 뒤 실행하고 상황판에서 본다. 지도는 실제 위성사진 느낌(구현 시 VWorld 영상지도 등). 금지구역 없음, 작전 지역 + 작전 구역만. 작전 구역은 작전 설정에서만 그리고 상황판에서는 바꿀 수 없다(하한선 규칙 2).

| 화면 | 하는 일 |
|---|---|
| 1 작전 만들기 | 이름·목적·시간 입력, 지도에 작전 지역과 작전 구역 그리기. 경로·지점은 시나리오에서 정함 |
| 2 기체 선택 | 공중·해상·지상으로 나눠 보기, 체공·센서·정비 상태 확인, 시작 위치 지정. 정비 중 기체는 선택 불가 |
| 3 시나리오 작성 | 템플릿(해안 경계, 고속 보트 추적, 수색·구조, 빈 시나리오), 역할 줄 3개(AIR/SEA/GROUND), step 카드, 액션 라이브러리 15개, 비상 단계 패널, **AI 초안 입력 칸(문장 → 초안 카드)**, 저장 전 확인(로직·보고 지점·배터리·구역), 기체 종류별 펼침 미리보기 |
| 4 시뮬레이션 | 저장한 시나리오를 지도에서 재생·일시정지(기본 세팅만). 단계별 진행과 기체별 예상 귀환 배터리. "사건 넣기" 버튼 없음. 가상 적 시나리오·반복 비교는 발전 항목 |

### 5.5 질의 대비 답 두 개(결정 불필요, 문서에만)
- **"경계 밖으로 달아나는 보트는 놓치는 것 아닌가"**: 군 부대는 어차피 NLL을 넘지 않는다. 시스템은 경계 끝에서 감시를 유지하고 마지막 위치·침로를 기록에 남겨 상급 부대·해경에 넘긴다. 구역 차단은 "추적 포기"가 아니라 "넘지 못하는 선을 운용자가 급해도 못 넘게 하는 것"이다.
- **"대드론 임무에는 어떻게 쓰나"**(대드론협회 심사위원): 탐지가 다른 기체의 역할을 낳는 구조는 같다. 레이더나 공중 기체가 미식별 드론을 탐지하면 보고 카드가 올라오고, 운용자가 "식별"이나 "추적 인계" 플레이를 고르면 시스템이 가능한 기체에 역할을 묶는다. 2022-12 북한 무인기 5대 침투 때 추적 중 레이더에서 놓친 사례가 근거다(06 보고서).

## 6. 시스템 구조

> **2026-10-09**: 6절·7절은 `docs/research/09-rolecall-implementation-foundation.md`로 대체됐다(결정 0003·0004 반영, 데이터 형식 확정 수준). 아래는 옛 내용이며 참고용으로만 남긴다.


### 6.1 큰 그림
화면(cop-ui, React) ↔ gateway(FastAPI, REST + WebSocket) ↔ 엔진. 시뮬레이션과 실행은 **같은 엔진**을 쓴다. 시뮬레이션은 기다림 없이 끝까지 돌린 결과를 재생, 실행은 0.2초 틱으로 실시간.

### 6.2 틱 순서
1. sim: 통과한 명령대로 기체 이동·배터리 감소, 사건 대본의 환경 사건 발생
2. sensing: 센서 범위 탐지, 보고 생성, 위치 이상 표시
3. runtime: 비상 조건 → 운용자 명령 → 기체별 현재 step 한 줄 진행 → 기체 명령 생성
4. safety: 모든 명령에 규칙 3개(출처 있음, 작전 구역 안, 귀환 배터리 충분) 확인, 통과/차단+대안. 수동 모드 기준선 집계는 runtime이 같은 틱에서 "기체별 직접 명령이었다면 몇 건인지"를 센다
5. gateway: 프레임(기체 상태·표적·보고·기록·숫자) 전송

### 6.3 편집기에서 기체 명령까지
1. 편집기가 플레이 형식 JSON으로 바로 저장(화면 좌표 포함).
2. play 모듈이 저장 전 확인(로직 오류, 귀환 배터리).
3. 배정 때 펼치기 표(액션 15 × 영역 3 → 기체 명령 8종 또는 불가)로 기체 종류별 명령으로 바꿈.
4. runtime이 틱마다 기체별 (플레이, step, 줄)을 한 줄씩 진행.

고정 목록:
- 액션 15: 지점 이동, 경로 순찰, 구역 수색, 귀환 / 표적 감시, 지점 감시, 표적 접근 / 통신 중계 / IF, 반복, 대기 / 신호 송신, 신호 수신 / 운용자 보고, 운용자 승인 필요
- 조건 6: 표적 발견(종류), 도착함, 시간 경과, 배터리 N% 미만, 운용자 선택, 신호 수신
- 기체 명령 8: 이동, 선회, 거리 유지, 정지, 경로 따라가기, 지그재그, 귀환, 중계
- 비상 규칙 4: 통신 두절(안전 지점 대기→중계 요청), 배터리 30% 미만(교대 요청→귀환), 위치 이상(정지→다른 기체가 이어받기), 운용자 호출(그 자리 감시 유지)
- 하한선 규칙 3(결정 0003): 출처 없는 명령 거부(승인 대기로), 작전 구역 밖 차단, 귀환 배터리 부족 차단+대안. 예외 허가 없음
- 인지부하 지표 3(결정 0003): 운용자 조작 수, 동시에 떠 있던 경보 최대치, 역할 공백 시간. 수동 모드 기준선은 같은 대본에서 엔진이 "기체별 직접 명령 수"를 센 값
- AI 초안 어휘: 위 액션 15·조건 6만 허용. 스키마 밖 출력은 버리고 다시 요청. 시연 문장 2개의 응답은 `demo/scenarios/`에 캐시

### 7.3 협업 규칙
1. 브랜치 이름이 수정 범위를 정한다(사람이 아님). 돕는 사람은 `<모듈>/<주제>` 브랜치만 만들면 된다.
2. 모든 액션은 contracts 타입 입력·출력 + 예시 JSON 테스트.
3. "도움 가능"(순수 함수)부터 가져간다. 핵심 상태 액션은 담당자가 끝까지.
4. 막히면 5분 안: 채팅에 "막힘: 액션 id, 증상" → 앞선 사람이 그 모듈의 도움 가능 액션을 가져감 → 공개 함수 시그니처는 바꾸지 않음.
5. 작업판은 12:00에 전부 채움(UI 행은 리드가 미리, Python 액션은 각자 사이클 시작 때 `new_action.py`).
6. 공유 파일: contracts는 리드만, demo/scenarios·pyproject는 누구나(채팅 알림).
7. 통합은 리드 주관, 늦은 파트는 예시 JSON 스텁으로 대체하고 통합을 미루지 않는다.
8. 원격 브랜치 없음. 로컬 main 병합 후 main만 push(`ship.sh`).

### 7.4 늦어지면 빼는 순서
- 공통: 작전 설정 화면 → 경보 묶기·GPS 교란 장면 → 시뮬레이션 지도 재생 → 배정 추천(고정 기체+이유 문장) → 편집기 반복·IF 묶음 편집.
- 끝까지 남기는 것: 편집기 카드·연결·저장, 보고와 대응, 이어받기, 플랜 주입, 직접 조종 차단, 숫자 4개.

### 7.5 대회 전 준비

## 9. 알려진 약점과 검증 안 된 가정(비판 검토용)
- **편집기의 새로움 부족**: 코드 없는 편집기는 이미 여러 제품에 있다. 차별성은 "조합"에 의존하며, 심사위원이 조합을 새로움으로 받아들일지는 검증되지 않았다.
- **배정·이어받기 규칙의 단순함**: 거리·배터리 점수식과 "할 수 있는 기체" 필터뿐이다. 브레이브버드(능력 벡터)보다 단순할 수 있다. 발표 주인공이 배정이 아니어야 하는 이유.
- **하한선 규칙 3개가 "보안적 하방"으로 충분한가**: 결정 0003으로 출처 거부·구역 차단이 추가됐지만 서명·재전송 방어는 여전히 범위 밖이다. 출처는 기록이지 위조 방지가 아니다. 심사에서 "출처를 위조하면?"이 나오면 "이번에는 감사 가능성까지, 서명은 다음"으로 답해야 한다.
- **작전 구역 무조건 차단이 임무를 방해할 수 있다**: Auto-GCAS의 "간섭하지 말라" 원칙과 부딪힌다. 고속 보트가 경계를 넘으면 추적을 포기하는 셈이다. 지휘관 예외 허가는 복잡해서 뺐으므로(사람 결정), 시연 대본은 "경계 안쪽 끝에서 감시 유지"가 합리적으로 보이게 짜야 한다.
- **AI 초안의 품질과 의존성**: 스키마는 맞춰도 작전으로 허술한 초안이 나올 수 있다. 시연은 캐시로 고정하지만, 심사위원이 즉석 문장을 요구하면 라이브 호출이 필요하고 결과를 보장할 수 없다. "저장 전 확인이 막는 장면"을 오히려 강점으로 쓴다.
- **인지부하 숫자**: 결정 0003으로 수동 모드 기준선과 지표 3개를 넣었다. 남은 약점은 기준선이 "사람이 실제로 조작한 값"이 아니라 "엔진이 센 가상의 직접 명령 수"라는 점이다. 발표에서 "같은 대본에서 기체별 직접 조종이라면 필요했을 명령 수"라고 정확히 말해야 한다. 역할 공백 시간의 정의(기체 이탈 시각부터 이어받기 시작까지)도 문서로 고정해야 한다.
- **시간 위험**: 3명이 24시간에 액션 85개는 많다. 편집기(React Flow)와 runtime 상태 기계가 병목이 될 가능성이 크다. 늦어지면 빼는 순서가 있으나 통합 1(18:00)을 못 넘기면 시연 자체가 흔들린다.
- **현장 근거의 출처 수준**: 해안 경계 실패 3건은 언론 보도 요약이다. 정부 조사 원문·감사 결과는 확인하지 못했다. NK News 2026-07 링크는 잘려 있어 재확인 필요.
- **장소 민감성**: 실제 접경 섬 위성사진 위에 가상 기지·표적을 그리는 것이 "실제 표적화 금지" 정책과 충돌하지 않는지 사람이 판단해야 한다.
- **시뮬레이션의 얕음**: 2D 등속 이동과 배터리 선형 소모뿐이다. 심사위원이 "실제 비행 소프트웨어와 연결되나"를 물으면 SITL 미사용을 설명해야 한다.
- **구현 전 문서가 많음**: 아티팩트 4개와 이 문서가 모두 구현 전 상상이다. 10/10 12:00 데이터 형식 고정 때 상당 부분이 바뀔 수 있다.
